## HIGH findings

### H-1. Task 14's locked invariants omit the one requirement the grounding dossier calls make-or-break: the **same-turn sweep + artifact surfacing**. As locked, a compliant implementation can still ship report/generate-submission artifacts the agent/user can never reach — and Task 15's exit-0 matrix will not detect it.

**Evidence:**
- Upstream contract: the sidecar returns staged paths that are **sidecar-container paths** (`/staging/<sha256(api_user)>/<request_id>/…`) inside the op result — `sidecar/app/ops.py:118-155` (`stage_bytes` → `result["saved_files"][key] = staged_path`), `sidecar/app/staging.py:77-100`. These paths are meaningless in the agent container. Upstream made the ops *functional* only via the host bridge's **same-turn sweep** (`src/dmac_assistant/staging_sweep.py`, invoked from `ws.py:281-291` *before* the turn's `new_files` diff), which copied `.complete`-marked request dirs into the agent's own scratch and surfaced them in the turn's reported artifacts. The wave's own grounding dossier states this verbatim: *"Whatever process replaces the host-run bridge … must replicate this same-turn sweep step, or the 7 ops' file-producing operations (`report`, `generate-submission`) will silently produce artifacts the agent can never read"* (`.superpowers/sdd/sidecar-dossier.md`, §3 "staging.py", final bullet).
- The wave's locked invariants (PLAN-7:864-877) require only: (i) user-scoped landing, (ii) no cross-user path from a WS frame, (iii) `_staging` subpath mount, (iv) sweep by trusted code. **No invariant requires the sweep to complete in-turn / before `run_cc_turn` publishes artifacts, nor that swept files appear in the turn's published artifact set.** An hourly janitor sweep satisfies all four invariants and still leaves every report/generate-submission artifact unreachable during and at the end of the turn that produced it.
- Task 15's `plugin_ops_matrix.json` records `{transport, exit_code, excerpt}` only (PLAN-7:892-896; SPEC-7 §8:223-230). A `report` op that stages into `_staging` and returns dead sidecar paths **exits 0** — the capability gate passes while the capability is absent. That reproduces exactly the failure mode the user ruled against ("an op that reaches the sidecar but still fails the user's bar").
- Internal contradiction: invariant (iv) offers "or the sidecar itself if it can prove per-request user scoping" (PLAN-7:875-877) — but the sidecar's mount is locked to the `_staging/` subtree only (invariant iii, PLAN-7:871-873), so the sidecar **cannot** write into `{project}/{user}/` at all. The alternative is dead on arrival as written; leaving it in invites an implementer to widen the sidecar mount "to make the option work".

**Fix direction:** add a fifth locked invariant: *sweep completes within the turn (post-op, pre-publish — the natural trusted trigger is `run_cc_turn`'s existing post-turn publish path in `cc_engine.py`, mirroring upstream `ws.py:281-291`), swept files land under the requesting user's subtree, and the turn's published artifacts include them; the op-result path payload must be translated (or documented as superseded by published artifacts).* Strike the "or the sidecar itself" clause. Extend the Task 15 matrix schema so `report`/`generate-submission` entries must additionally record a validator-checkable swept-artifact path under the user's own subtree (e.g. cross-check against `subpath`-consistent prefix), not just exit 0.

### H-2. Task 15 Step 2's closed-set `dmac-cc-net` membership rule is **not implementable from `network_inspect.json` as produced**: transient agents have *random Docker names* and `docker network inspect` exposes **no labels** — "plus containers labeled `nextseek.cc.run=*`" cannot be evaluated, so the check will either fail every live bundle or be implemented vacuously.

**Evidence:**
- PLAN-7:897-900 / SPEC-7 §10:276-278: closed set {nginx-pattern, `dmac-bedrock-proxy`, `nextseek-sidecar`} "plus containers labeled `nextseek.cc.run=*` — anything else fails".
- The artifact contains **names only**: harness capture is `docker network inspect <net> -f '{{range .Containers}}{{.Name}} {{end}}'` → `{"containers": [names]}` (`test_cc_realstack.py:106-109, 190`). Full `docker network inspect` JSON also carries only Name/EndpointID/Mac/IP per container — never labels.
- Agent containers are spawned **without `name=`** (`cc_engine.py:355-373` — labels set, no name), so their runtime names are Docker-random (`eager_wozniak` style). A validator seeing `["nextseek-nextseek_nginx-1", "dmac-bedrock-proxy", "nextseek-sidecar", "eager_wozniak"]` cannot distinguish the legitimate agent from a planted stranger. Under a strict closed set the honest bundle **fails**; the only names-only "fix" is allowing arbitrary unknown names — i.e. an open set, defeating the check.
- The seam is already fragile pre-wave: `check_agent_container_in_network_inspect` (`validate_step7_compose_deploy.py:849-859`) requires `run_id` as a substring of `network_inspect.json` — with random agent names that too is unsatisfiable from an honest `docker network inspect`, inviting the harness to inject `run_id` into the JSON itself (self-referential, gameable). The wave builds a stronger rule on the same broken artifact instead of fixing the seam.

**Fix direction:** specify the mechanism in Task 15 Step 2: either (a) `cc_engine._run_kwargs` gains `name=f"dmac-cc-agent-{run_id}"` (hermetically testable; makes both the run_id cross-check and the closed set enforceable from names alone — closed set then = trio + `^dmac-cc-agent-` prefix, with the run_id name required to match `meta.json.run_id`), or (b) the harness captures a second artifact (`docker ps --no-trunc --filter label=nextseek.cc.run=<run_id> --format ...` plus full network inspect keyed by container **ID**) and the validator joins them by ID. Option (a) is smaller and self-verifying; either way the plan must say which.

### H-3. The 9/9-exit-0 live bar is **not achievable on the MBP greenfield gate as planned**: several ops require pre-existing NExtSEEK data and server-side LLM providers that no task provisions, and the matrix run's server-side spend is outside every budget control. Unachievable gates get gamed — this is the wave's own gameability thesis applied to itself.

**Evidence:**
- `report` requires an existing project (`granular.py:120-128` — `run_reporter_summary(config, ReporterPlan(project=…))`); `generate-submission` requires real sample UIDs (`granular.py:131-146`); `api-write` requires a writable sandbox entity (design deferred to "recorded in the report, vetting sharpens it", PLAN-7:902-906); a sensible `api-read` needs a parser_plan targeting a real endpoint with data. On a **greenfield MBP** (fresh SEEK/MySQL/Neo4j — the whole point of Task 10 Step 0's pre-bootstrap absence checks) none of these entities exist, so honest runs of report/generate-submission/api-write plausibly exit 3/4, failing the bundle. The wave defines a sandbox-entity design point for **write** ops only; it says nothing about seeding a project/samples for the read/report ops. No task owns MBP data seeding.
- Server-side dependency: every sidecar-backed op ultimately runs NExtSEEK-side **LLM agents** (`granular.py:61-146` — `entity_agent`/`parser_agent`/`graph_agent`/`api_agent_build_request`/`report_writer_agent` via `chat_nextseek`; the file's own comment cites "Bedrock/Opus Converse" for report_writer). So the MBP live gate now additionally requires a working `GCP_API_KEY` (and server-side Bedrock reach) in `docker/nextseek.env` plus egress — a new live-gate prerequisite stated nowhere in the wave's permissions table (PLAN-7:927-933) or Task 7/8 blast radius.
- Spend: `budget_cap_usd`/`forced_cc_result.json.cost` caps only the forced CC turn; 9 matrix ops × server-side LLM calls (entity runs 3× across entity/parse/graph) are unmetered and unrecorded in `meta.json`.

**Fix direction:** add an explicit Task 15 (or Task 10) substep: minimal seeded fixture (one sandbox project + N sample UIDs, created via the authenticated REST API as the gate user, recorded in evidence) that all data-dependent ops target; document acceptable empty-data semantics per op where seeding is impossible; add the GCP/Bedrock server-side env prerequisites to Task 7's key list and Task 8's prerequisites; record matrix spend (even best-effort) in `meta.json`.
