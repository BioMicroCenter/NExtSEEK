## HIGH findings

### R2-H1. The in-turn matrix → in-turn sweep → `published_path` chain is structurally unachievable under `cc_engine`'s **hard-capped 180 s turn**, and the new fifth invariant itself forbids the only cross-turn recovery path. As specced, every honest MBP bundle fails the wave's flagship gate. (Thread G re-raise — **PARTIAL**, parent iter-1 H-1; the infeasibility is introduced by the combination of hardener-added texts.)

**Evidence (all verified against source):**
- `cc_engine.py:70-74`: `_TIMEOUT_HARD_MAX = 180` and `_DEFAULT_TURN_TIMEOUT = min(env, 180)` — the turn wall-clock is **hard-capped at 180 s and cannot be raised by env** ("project rule"). The watchdog (`cc_engine.py:583-593`) stops + force-removes the container on overrun and `run_cc_turn` returns a `query_error` **before** the publish path (`:627-633`) — no sweep, no publish, and `forced_cc_result.json` becomes an error (bundle fails anyway).
- The turn otherwise ends when the CC process finishes its trivial sentinel prompt (read loop `:606-624` breaks, publish runs `:638-643`, `finally` force-removes `:720-729`). The harness controls neither bound: the honest exec window for the matrix is "however long a one-file sentinel turn happens to run," realistically well under a minute.
- Into that window Task 15 Step 3 (PLAN-7:979-983) puts **9 sequential `docker exec` ops**, 7 of which invoke NExtSEEK-side LLM agents (`granular.py:61-143` — `parse` = 2 LLM calls, `graph` = 2 LLM calls + Neo4j, `report` = reporter + summary + artifact download/staging, `generate-submission` = Bedrock/Opus report writer; upstream sizes a **300 s recv timeout for a single op**, `_sidecar_client.py:41`). Nine ops inside a ≤180 s turn that must also boot CC and answer the prompt is arithmetically out of reach; even `report` + `generate-submission` alone are marginal.
- The `published_path` requirement (PLAN-7:964-968; SPEC-7 §8:234-236) needs those ops' staged artifacts to be **swept by this same turn's end** (fifth invariant, PLAN-7:924-934). And the invariant expressly rules out the natural recovery: "Any sweep schedule other than in-turn (janitor, hourly, **next-turn**) FAILS this invariant" — so artifacts staged after the turn's publish can *never legitimately* acquire a `published_path`. The two hardener-added texts (invariant + matrix cross-check) close iter-1's H-1 hole and jointly create a gate no honest run can pass.
- The plan is silent on `turn_timeout` everywhere: the wave never mentions the 180 s cap, no keep-alive contract for the forced-turn prompt, no per-op-timeout-sum ≤ turn-window arithmetic, no parallel-exec design, no decoupled second gate turn.

**Why this matters at the user's bar:** "no unachievable or gameable gates." An unachievable REQUIRED artifact chain gets one of three endings: the hard cap is quietly raised (eroding an engine safety bound), the matrix is run outside the turn and the provenance/sweep checks are loosened to let it pass (the facade failure mode again), or the wave stalls. All three are exactly what this amendment exists to prevent.

**Fix direction (pick one explicitly; all are small texts but they are design decisions):**
(a) **Dedicated capability-gate turn:** run the matrix during a *second* forced turn whose prompt instructs the agent to execute a harness-provided op script and wait on a `MATRIX_DONE` marker; amend the wave to permit (with sign-off) a documented, gate-only `NEXTSEEK_CC_TIMEOUT_SECONDS`/`turn_timeout` override above 180 s **for this turn only**, with the sum of per-op timeouts pinned < turn_timeout − slack; sweep-at-turn-end then works unchanged. Or (b) **decouple publication proof from the forced turn:** allow the harness to invoke the same trusted sweep function (`cc_engine`/Django, not agent, not sidecar) once, immediately after the matrix completes, recording the invocation in evidence — and reword the fifth invariant so the in-turn requirement binds the *production* flow while the gate flow uses the same trusted-code sweep with explicit provenance. Either way, state the 180 s interaction in Task 15 and add the failure mode ("watchdog kills mid-matrix") to the wave risk register.

## MEDIUM findings

### R2-M1. `network_inspect.json` cannot support the new checks as captured today: it is written **after the turn** (agent already force-removed, so the deterministic name is absent) and contains **names only** (no container IDs), while the matrix join is specced "on container id/name" with rows that carry an **id but no name**. Capture timing and format are amended nowhere. (Thread H re-raise — PARTIAL, parents iter-1 H-2/M-4.)

**Evidence:** harness capture is `docker network inspect <net> -f '{{range .Containers}}{{.Name}} {{end}}'` → `{"containers": [names]}` written **after** `t.join` (`test_cc_realstack.py:106-109, 167, 189-190`); the agent is force-removed in `run_cc_turn`'s `finally` (`cc_engine.py:720-729`), so a post-turn inspect can never contain `dmac-cc-agent-<run_id>`. Yet Task 2's locked correlation check still requires "agent container in network inspect" (PLAN-7:137) and Task 15 Step 2 says the run_id-substring check "is REPLACED by the deterministic agent-name match" (PLAN-7:974-976) — a presence check that is only satisfiable if capture moves **in-turn**, which no wave text states (contrast: the isolation scan needed an explicit "capture DURING the turn" amendment for exactly this trap, PLAN-7 Task 10 Step 4). Separately, matrix rows are `{op, transport, exit_code, excerpt, container_id, image, wall_secs}` (PLAN-7:955-956) — no name — while the artifact has no ids, so the specced "join on `network_inspect.json` on container id/name" (PLAN-7:957-959; SPEC-7 §8:229-231) has **no common key**.
**Fix direction:** one paragraph in Task 15 Step 3: capture `network_inspect.json` as the **full** `docker network inspect dmac-cc-net` JSON (Containers keyed by ID with Names), **during the turn** (same poll window as the isolation scan); add `container_name` to matrix rows; validator joins matrix `container_id` → inspect key → Name and requires Name == `dmac-cc-agent-<run_id>`.

### R2-M2. The "separate harness container" executor alternative is dead on arrival — the same DOA-clause class the hardener struck for the sidecar-sweeper: any such container either appears in `network_inspect.json` with a name outside the closed set (bundle fails) or is absent from it (matrix attachment join fails), and it cannot be named `dmac-cc-agent-<run_id>` (name collision with the live agent). (Hardener-added contradiction; threads G+H.)

**Evidence:** SPEC-7 §8:226-228 / PLAN-7:981-983 (alternative permitted "ONLY with identical image + network + env and its own docker inspect provenance recorded") vs Task 15 Step 2's closed set (PLAN-7:969-974: allowed = nginx pattern, `dmac-bedrock-proxy`, `nextseek-sidecar`, `^dmac-cc-agent-<run_id>$` — "anything else fails") vs the matrix executor-attachment requirement (PLAN-7:957-959). It also does not dodge R2-H1: ops run in a separate container still stage into the same `_staging` and still need the turn-end sweep. Leaving it in invites an implementer to widen the closed set "to make the option work" — iter-1's own warning pattern (H-1 bullet 4).
**Fix direction:** strike the clause, or spec it concretely: a reserved second allowed name (`dmac-cc-matrix-<run_id>`, harness-spawned with recorded provenance) added to the closed set and to the sweep design chosen for R2-H1.

### R2-M3. **Fix direction:** pin the hatch to **exit 0 with a documented empty-result excerpt shape** (empty rows/empty saved_files) — never a documented nonzero exit; if any op genuinely cannot exit 0 on the fixture, that is a fixture defect Task 15 Step 3b must fix by seeding more, not a validator allowance.

### R2-M4. Matrix anti-fabrication binding is still absent: `container_id`, `image`, `wall_secs`, and excerpts are all self-reported by the harness with **nothing unpredictable tying the rows to this run** — unlike the isolation scan, which got an agent-authored per-run live sentinel for precisely this reason. The iter-1 M-4 remedy (provenance fields) pins *shape*, not *authenticity*. (Thread H re-raise — PARTIAL, parent iter-1 M-4.)

**Evidence:** per-op record PLAN-7:955-956; the gameability row's remedy is "harness-written from subprocess stdout; … run_id cross-correlated" (PLAN-7:1044) but no matrix field or companion artifact carries the correlation (the proxy-log run_id check covers the forced turn's Bedrock calls, not the 9 op executions; the 7 sidecar ops traverse `nextseek-sidecar → nextseek_nginx → Django`, which never touches the proxy log). A row set copied from a dev-VM run (with the MBP run's `container_id` pasted in) passes every specced check except the `published_path` prefix — which is a string assertion, not an on-disk check. Phase-2 precedent on this plan accepts harness-honesty ONLY when paired with an in-bundle unpredictable cross-check (Task 10's `LIVE_<sentinel>`/`OWN_<run_id>` pattern, PLAN-7:137).
**Fix direction:** cheapest real binding: require each op invocation to pass a per-run nonce argument that the *server-side* handler echoes into its response (already true for several ops' request/response payloads — e.g. `query` echo fields), and/or add a REQUIRED `nginx`/Django access-log window artifact for the run showing the 7 assistant-endpoint hits inside the gate window, validator-matched per op; at minimum require `published_path` files to be listed in a harness-captured post-sweep `find` of the user subtree (an artifact, not a bare string).
