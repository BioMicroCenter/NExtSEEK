## Adjudication of the five iter-2 hardening items

### 1. Gate executor design (R2-H1 / R2-M2) — **mechanism sound; two residues (M-1, M-2) and one contradiction (M-3)**

Verified: `_TIMEOUT_HARD_MAX = 180` with env clamped by `min(..., _TIMEOUT_HARD_MAX)` (`cc_engine.py:70-73`) — the cap is real and the wave does not relax it. `run_cc_turn`'s watchdog stops/force-removes on overrun and the `finally` block force-removes on every exit, so the in-turn matrix was indeed impossible; the dedicated executor + single trusted sweep entrypoint (PLAN-7:948-958) is a coherent fix. The production in-turn sweep is separately enforced: Task 14's hermetic tests pin "a fake-staged `.complete` dir surfaces in the same simulated turn's publish set" (PLAN-7:945-947), and the pinned hook location (post-loop, pre-`_publish_artifacts`) matches the actual publish path in `run_cc_turn`. The gate invokes the *same* entrypoint — same trusted code path, explicit provenance. No facade reintroduced on the sweep leg. The reserved name `dmac-cc-matrix-<run_id>` cannot collide with the agent name (different prefix) and is in both closed sets (SPEC-7 §10:301-302; PLAN-7:1009). The old DOA "separate harness container" alternative is gone from §8.

**Residue (a) — executor env is asserted, never machine-checked (M-1).** "Same agent env contract (gate user's own creds + sidecar/topology vars; NEVER shared secrets)" (PLAN-7:1020-1022; SPEC-7 §8:233-234) is exactly the claim the wave elsewhere refuses to take on faith: the forced-turn agent gets `agent_env_scan.txt` + the shipped `check_agent_env_decredentialed` oracle (`validate_step7_compose_deploy.py:813-822`) and hermetic `test_cc_engine_env.py` guards on `build_agent_environment`. The executor is harness-spawned and therefore **bypasses `build_agent_environment` and every hermetic leak test built on it**, yet no §8 artifact scans its env. "Recorded `docker inspect` provenance" does not close this: if it means id/name/image only, the env is unverified; if it means full inspect JSON, `Config.Env` carries the gate user's `NEXTSEEK_PASSWORD` unredacted and trips the §9 secret scan — either reading is broken. Executor cleanup is also unpinned ("harness controls executor lifetime" — no removal requirement; a crash leaves a credentialed container parked on `dmac-cc-net`).

**Residue (b) — gate/production fidelity on the turn cap (M-2).** The executor deliberately runs ops **outside** the 180 s cap (per-op timeout pinned, harness-controlled lifetime), while every production op invocation runs *inside* a watchdog-killed 180 s turn. The wave's own text sizes single ops at up to 300 s recv (`_sidecar_client.py:41`, cited at PLAN-7:954-955). An op whose `wall_secs` is ≥ (or near) 180 s passes the gate yet can never complete in any real turn — from the user's seat, that capability is absent, which is the exact condition the G7-11 ruling ("Step 7 is incomplete while any shipped plugin op lacks a working backend") exists to catch. `wall_secs` is recorded per row but **no check evaluates it against the turn budget**.

### M-2. The gate proves ops in an uncapped executor while production ops must complete inside the 180 s hard turn cap; `wall_secs` is recorded but never evaluated, so an op that can never finish in any real turn still passes the capability gate. (Thread G — PARTIAL, parent iter-2 R2-H1; the fidelity gap is the flip side of fix (b).)

**Evidence:** `_TIMEOUT_HARD_MAX = 180`, env-clamped (`cc_engine.py:70-73`); watchdog stop/force-remove on overrun. Production ops run as agent subprocesses inside that bound; the wave itself sizes single ops at up to 300 s recv (PLAN-7:953-955). Task 15's per-op timeout bounds *spend*, not production fit; no validator check, success condition, or even risk-register row relates `wall_secs` to the turn budget. Under the user's ruling ("incomplete while any shipped plugin op lacks a working backend"), an op with `wall_secs` ≥ 180 s has a working backend the deployed assistant can never actually use — the gate certifies a capability the product can't deliver, which is the facade class this amendment exists to kill.
**Fix direction:** one validator check: flag/fail any matrix row with `wall_secs` ≥ the engine turn cap (read from a recorded `meta.json.turn_cap_secs` or the pinned 180), requiring an explicit documented disposition (e.g. async/multi-turn usage pattern with user sign-off) rather than a silent pass; note the interaction in the wave risk register.

### M-3. Task 15 Step 3's "(or the agent name if an op was legitimately exec'd in-turn)" contradicts the spec of record and reopens the executor-provenance seam the closed set just sealed. (Thread H — REGRESSION, parent iter-2 R2-M2 hardening.)

**Evidence:** SPEC-7 §8:236-239 requires the join to yield `Name == dmac-cc-matrix-<run_id>` — no alternative; §8:232-235 states "the matrix CANNOT run inside a live turn." PLAN-7:1032 nevertheless permits rows to join against the *agent's* name. The branch is (a) unusable legitimately by the wave's own arithmetic (that's why the executor exists), (b) undefined — it never says which inspect file agent-name rows join against, and "legitimately" is not validator-decidable, and (c) exploitable: a fabricator can stamp every row with the real agent's `container_id` (present in the during-turn inspect they already captured) and skip spawning an executor at all, downgrading the provenance leg to pure text-artifact forgery. This is the same DOA-alternative class the loop struck twice already (iter-1 sidecar-sweeper, iter-2 R2-M2).
**Fix direction:** strike the parenthetical (all 9 rows join `network_inspect_matrix.json` → executor name), or pin it precisely: which ops (at most the 2 viewset ops), which inspect file, and a machine-checkable marker replacing "legitimately".
