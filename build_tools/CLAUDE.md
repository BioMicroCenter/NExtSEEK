# `build_tools/` — what will bite you

## Invariants

- Never hand-edit text between a `PLAN005-GEN` BEGIN/END pair anywhere in the repo: the next `--write` overwrites that region from the registry, and until then `--check` reports the tree as stale (`build_tools/gen_op_surfaces/emit.py:238-258`).
- A marked file must carry exactly one BEGIN and one END, ordered and unnested; a duplicate or inverted pair raises `MarkerError`, which aborts the whole run rather than that one target (`build_tools/gen_op_surfaces/blocks.py:11-31`).
- The `NEXTSEEK-DOCS` region of `docker/cc-runtime/container/CLAUDE.md` must come through inventory generation byte-identical; the guard compares it before and after and refuses the render otherwise, which is the only thing keeping the two generators that share that one file from clobbering each other (`build_tools/gen_op_surfaces/claude_md.py:56-63`).
- No `PLAN005-GEN` marker may sit inside that docs block: the same guard refuses, because the docs ingester replaces everything between its own markers and would silently eat a nested op inventory (`build_tools/gen_op_surfaces/claude_md.py:47-53`, `build_tools/ingest_nextseek_docs/toc.py:79-81`).
- The named-context `COPY` must stay the last writer of the in-image capabilities path; add any later `COPY` landing on `/app/plugins/nextseek` and validation raises rather than letting an image ship the plugin tree's own copy of that file (`build_tools/gen_op_surfaces/docker_blocks.py:117-159`).
- The Compose named context for `chat_nextseek` must resolve to the vendored tree inside the repo root; an absolute path, a `~`, a `..` segment or any other resolved target is refused, so a build cannot be pointed at an out-of-tree checkout (`build_tools/gen_op_surfaces/docker_blocks.py:162-198`).
- Generated paths are resolved through a guard that rejects absolute paths, `..` traversal and symlinks whose target leaves the root; without it a crafted target path would let a generator write outside the repository (`build_tools/gen_op_surfaces/paths.py:12-37`).
- The Plan 005 coverage floor cannot be argued down: a `--min-total` below the constant raises before anything is measured, so lowering the bar requires editing the constant and showing up in review (`build_tools/plan005_gate.py:362-363`, `build_tools/plan005_closeout.py:24`).
- Coverage-scope narrowing is refused outright — an `omit` list, an `exclude_also`, a narrowed source or a disabled branch flag each raise — and a `.coveragerc` or `[tool.coverage` section that did not exist at the base commit is rejected as well (`build_tools/plan005_gate.py:96-107`, `build_tools/plan005_gate.py:197-207`).
- Whatever these tools rewrite must be committed in the same change: the image `COPY`s the docs snapshot and the container `CLAUDE.md` straight out of the checkout (`docker/cc-runtime/Dockerfile:63-64`), so an uncommitted regeneration means the built image silently ships the previous content and no build step will refetch it.
- This file exists in git only by an explicit un-ignore: a bare `CLAUDE.md` pattern ignores every such file in the tree and this one is carved back out by exact path, so renaming or moving it makes it silently untracked (`.gitignore:189`, `.gitignore:210`).

## Landmines

- The baked capabilities copy is stale **right now**, and it is the single most expensive defect in this directory. `docker/cc-runtime/build_context/plugins/nextseek/context/capabilities.md` is 11747 bytes against the canonical's 12128, first differing at byte 1958, and the missing region is a five-line Publication entry documenting `DOI` and `PMID` on the Study node (measured 2026-09-03 with `wc -c`, `cmp` and `diff` over the two paths named at `build_tools/gen_op_surfaces/constants.py:8-13`). Until it is repaired, `--write` rewrites the baked copy from the canonical on the next run rather than preserving whatever a maintainer intended by editing it (`build_tools/gen_op_surfaces/emit.py:81-88`), and every consequence below follows from the same five missing lines.
- That drift blocks regeneration of an unrelated file. `route_capabilities.json` cannot be emitted at all while the two capabilities documents differ, because the payload builder raises on the byte comparison before it reads any evidence, so the router's capability document is frozen until the drift is repaired (`build_tools/gen_op_surfaces/route_capabilities.py:229-232`).
- A byte-identity gate for that file **does exist**, in three independent places, and none of them blocks a merge: the whole-file comparison inside check mode (`build_tools/gen_op_surfaces/emit.py:288-295`), the payload precondition above, and a dedicated unit test (`build_tools/tests/unit/test_gen_op_surfaces.py:148-151`). All three are red, and all three are recorded as expected failures at `ci/pytest-baseline.txt:27-37`, inside a job whose pytest step is `continue-on-error` (`.github/workflows/ci-pytest.yml:45-46`).
- The two schema documents beside that file have **no gate at all**. `min_graph_schema.json` and `neo4j_schema.json` exist in both the canonical `chat_nextseek` context and the baked plugin context and differ there too (6860 against 4165 bytes, and 13801 against 13542, measured 2026-09-03); a grep for either filename across the whole of `build_tools` returns no match, so neither is a generated target and no run compares them. Unlike capabilities.md they have no Dockerfile override either, so the stale bytes are what the image actually ships (`docker/cc-runtime/Dockerfile:50-51`).
- `--check` does not fail cleanly on the drift. `RouteCapabilitiesError` is a `ValueError`, not a `SystemExit`, so it escapes the CLI's handler and the operator gets a Python traceback and exit 1 instead of the `gen_op_surfaces failed:` message the module writes for every other error (`build_tools/gen_op_surfaces/__main__.py:48-63`).
- The docs ingester **deletes** before it writes: every `*.md` in the target directory except `README.md` is unlinked, so a hand-authored note dropped into `docker/cc-runtime/docs/nextseek/` is destroyed on the next successful run (`build_tools/ingest_nextseek_docs/__main__.py:64-68`).
- The ingester's own page validator has blocked a real run before: the port record shows it rejecting live GitBook pages on 2026-07-01 for not starting with an H1, after a successful HTTP 200 fetch, and the committed docs were taken from the pinned source clone instead (`docker/cc-runtime/PORT-EVIDENCE.json:23-26`, `build_tools/ingest_nextseek_docs/fetch.py:157-162`). A refresh attempted today may therefore abort with zero writes and leave the snapshot silently frozen. <!-- UNVERIFIED --> whether the current GitBook export clears that validator needs a live fetch of a third-party site, which this repository cannot establish.
- Both ingester output defaults are relative paths, resolved against the current working directory (`build_tools/ingest_nextseek_docs/constants.py:14-15`). Run it from anywhere but the repo root and it silently creates a fresh `docker/cc-runtime/...` tree under your cwd and reports success.
- Three tests shell out to `git show` against a hardcoded revision (`build_tools/tests/unit/test_gen_op_surfaces_claude_md.py:66-67`, `build_tools/gen_op_surfaces/constants.py:36`). They fail with `CalledProcessError` in any environment where that object is unreachable — a shallow clone, or a container mount whose worktree gitdir points outside it — and the failure looks like a content drift rather than a missing history.
- One developer's home directory is hardcoded in this directory, on 7 lines of `build_tools/plan005_closeout.py` (10 raw occurrences) and once more at `build_tools/plan005_record.py:504`, and `/home/taishajo` does not exist on this host. Measured for this boundary on 2026-09-03 the blast radius on the test lane is **zero** — every failing test here fails for another reason — but the cost is worse than a red test: `--repo-root` and the evidence root default to paths nobody else has (`build_tools/plan005_closeout.py:25`, `build_tools/plan005_closeout.py:29`), and three docker argv templates bind-mount a `.git` directory from that home, so the closeout containers cannot start anywhere else (`build_tools/plan005_closeout.py:173`, `build_tools/plan005_closeout.py:406`, `build_tools/plan005_closeout.py:484`).
- A committed sign-off has gone stale against the file it approved. `build_tools/plan005_signoffs/task-09-compose-dockerfile.json:9` records a sha256 for `docker-compose.yml` that no longer matches the file, so any sign-off authentication run raises `made against earlier bytes` and two tests are red for that reason alone (`build_tools/plan005_closeout_control.py:496-500`). The Dockerfile hash in the same record still matches, so only half the record has rotted.
- The Plan 005 docker lanes cannot run here at all: both pinned digests are absent from this host's daemon (`docker image inspect` on each, checked 2026-09-03), and the validator refuses any substitute image rather than falling back (`build_tools/plan005_validate_plugins/validate.py:73-78`, `build_tools/plan005_closeout.py:15-20`).
- The gate couples to test modules in another package by **path string**, which no importer grep will find: `build_tools/plan005_gate.py:26-28` names two modules under `nextseek_api/cc_assistant/tests/` and one under `nextseek_api/assistant/tests/`, and `build_tools/plan005_gate.py:210-220` routes each to its own JUnit lane. Rename or move either cc_assistant module and it falls into the generic bucket, so its node IDs go missing from the lane the gate expects and the run fails with a misleading "missing from JUnit" error rather than a rename notice.
- Regenerating surfaces is step 7 of a longer sequence, not a standalone action: the registry export must run first, or the generators render an inventory that disagrees with the committed `ops.json` (`.claude/skills/add-cc-op/SKILL.md:66-83`).
