# Working in NessieAI/ns/

## Invariants

These are covered by tests. Breaking one is a security or data regression.

- **Only the boolean `True` confirms a write.** The gate compares by identity, and the request model in `nextseek_api/assistant/models_api.py` refuses coercion. Accepting `"true"` or `1` lets an unconfirmed mutation reach the database of record.
- **The gate fires before the agent.** In both the read and write paths of `granular.py` the gate check precedes the agent call. Moving it below turns a refusal into one that already spent tokens and touched the endpoint.
- **This is the only place the read allowlist is enforced on the agent's path.** The sidecar kept only the confirmation check. Softening `write_gate.py` removes the last check, not a duplicate.
- **An unknown op label is denied, and the known-label set is smaller than the dispatch table.** A new handler that calls the gate with its own label is refused until the label is added.
- **`run-ls` refuses any directory outside the cluster runs root**, and shell-quotes its argument. An unvalidated `run_dir` is an arbitrary read of the shared Luria account.
- **`run-checksum`'s `--paths` is caller-supplied, not a glob match, so an escape is a hard `OpValidationError`, never a silent `skipped` entry.** A traversal, a symlink, a hardlink, or a symlinked-ancestor resolve mismatch are all checked (the last three remotely, over SSH, since the read already happens on the cluster) and raised together in one message; only a genuinely missing/non-regular-file path is reported in `skipped`. See `NessieAI/tests/ns/reingest/test_run_checksum_op.py`.
- **`run-checksum`'s optional `manifest_id` must have been harvested from the same `run_dir` being hashed, checked with `os.path.normpath` on both sides before the SSH hash runs.** `run_dir` and `manifest_id` are two independent caller-supplied values off the same CC turn, and nothing else ties them together: a session that reingests run A then run B, but passes run A's stale `manifest_id` while hashing run B's files, would otherwise merge run B's digests into run A's manifest — and since relative output paths collide across nf-core runs by construction, `_primary_output` would then ship run B's digest as run A's measured `Checksum_PrimaryData`. A mismatch is a hard `OpValidationError`, never a silent merge. See `NessieAI/ns/granular.py`'s `_run_checksum`.
- **`run-harvest` covers Nessie-launched runs only.** It refuses a `run_dir` with no `PipelineRun` before staging anything, and it is the only code that sets `RunManifest.launch_record_id`. A run whose launch bookkeeping failed (`record_launch` is best-effort) therefore cannot be reingested for upload. See `NessieAI/tests/ns/reingest/test_run_harvest_op.py`.
- **A manifest without a launch record is test-only.** `build-upload-xlsx` builds it only for `is_superuser`, every build record carries `test_only`, and `upload.verify` refuses any record whose `test_only` is not exactly `False`. The flag comes from how the manifest was made, never from its `run_dir` string. A record or manifest saved before this rule has no `test_only` of `False`, so it is refused until the run is harvested again.
- **A chat answer may fill only a flagged, empty, non-run-sourced cell.** `answers.check_fill` derives the writable set from the first QA pass's findings and refuses any attribute the map sources from the run (`run_sourced_attributes`), even when a finding names it. It is an allowlist from the findings, not a denylist of measured names: a measured attribute added to a map later is unwritable by default. Two answers on one cell conflict and refuse the whole call. The structural keys and both checksums are never fillable (`NEVER_FILLABLE`). A place never overwrites: `check_place` refuses a run-sourced attribute, a data file, its checksum or its link (`NEVER_PLACEABLE`), and any attribute a targeted sample already holds in NExtSEEK, read by the injected `existing_values` lookup (`reingest_lookups.attribute_values_for_uids_strict`); a failed lookup refuses the place, never allows it. See `NessieAI/tests/ns/reingest/test_answers.py`.
- **`upload-reingest` uploads only a hash-matched build record of the current user.** `upload.verify` re-hashes each workbook against its build id and refuses a changed, blocked, foreign, test-only or project-less build, a second build of one `(sample_type, mode)`, and builds from more than one `manifest_id`, before any job starts. It sends files, never `rows`, and every job it starts sets `keep_assay_links`: a backfill's ASSAY sheet is empty, and the update path otherwise removes every assay link the sheet does not list, taking the sequencing samples out of their studies. `upload.run` then stages every workbook and re-hashes each staged copy against its build id before any job starts; one mismatch or staging failure removes every copy and refuses the call. Disposition is an allowlist (`CLEAN`, `SOFT_FLAG`), not a denylist of `HARD_REJECT`. Before staging, it creates the study assays its records list (`create_study_assay`), rebuilds those records, and uploads a rebuild only when `workbook_diff.assay_only_changes` finds nothing beyond Assay rows for the new assays: the reviewed workbook shows each assay to create as its planned label (`assay_plan.planned_assay_label`, not an int, so the parser refuses it as it stands), and the rebuild must hold that assay's created id in its place; after a new-mode job succeeds it registers the record's `parent_assays` (`register_parents`). A failed create refuses the call before anything starts; a failed registration is reported, never raised, and every case where parents were not added is said in the reply. `verify` refuses any record with `rebuilt_from`: a rebuild is uploaded only inside the call that made it, after that comparison. Both seams are the host's (`nextseek_api/services/reingest_assays.py`). `create_study_assay` first reuses the study's one assay tagged with the house assay, or adopts one untagged assay of the new title (a create SEEK did not confirm), and creates one only when neither exists. A reused or adopted assay must be in one of the caller's projects (`_require_in_scope`); a fresh create is sent to SEEK as the caller, so SEEK's own rights check on the study decides it. `register_parents` sends only the pairs whose assay is in the caller's projects, and reports the rest as not made.
- **`upload-reingest` uploads a build only from a later turn of the chat it was shown in.** `build-upload-xlsx` stamps each build record with `shown_in`, the chat turn it ran in, and `upload.verify` refuses a build with none, one from another chat, one from this turn or a later one, and one whose build turn did not complete (its reply never reached the user). Both turns come from the host's own records (`nextseek_api/assistant/chat_turns.py`, handed in as the `chat_turn` and `turn_delivered` seams), never from the agent, and a call from no single running Container-CC turn is refused. It is the server-side twin of the pipeline agent's `_launch_unconfirmed`. A record saved before this rule has no `shown_in`, so it is refused until the run is built again. See `NessieAI/tests/ns/reingest/test_upload_reingest.py`.
- **`upload-reingest` calls the gate first, under the `api-write` label.** It is transport-only like the other reingest ops, but write-class. The SEEK identity is resolved lazily, after the gate, so an unconfirmed call never looks it up. A failed job start reports only its exception class to the caller; the detail stays in the server log.
- **A build record names its caller and its own id.** `build_records.load` accepts only a positive int user id and `write` is atomic; `upload.verify` refuses a record whose `built_by_user_id` or `build_id` does not match. A build with no signed-in user is filed under `anonymous`, which `load` never reads.
- **A rendered workbook's artifact key is word characters only.** The download route accepts nothing else.
- **`build-upload-xlsx` never writes to NExtSEEK.** It returns a reviewable workbook; a hard-rejected sample type is skipped with its report.
- **`build-upload-xlsx` never builds a new sample that is already there.** In new mode a row whose data file is already a sample of its type under the same Parent, in one of the projects the caller's upload may write to (`reingest_lookups.caller_project_scope`, SEC-001), (the same non-empty `Checksum_PrimaryData`, or the same `Link_PrimaryData` when either side has no checksum) is left out and named in the reply, and a type with no rows left gets no workbook (`reingest_lookups.existing_uids_for_primary_files_strict`). The Parent is part of the match because a per-run output is the same file on every row. The same path with a different checksum is a run redone in the same folder: the row is built and the reply names the older sample; a reanalysis in its own run folder matches nothing. The lookup is strict: an outage stops the build rather than reading as nothing uploaded. See `NessieAI/tests/ns/reingest/test_build_already_present.py`.
- **The upload workbook emits all four sheets**, even empty ones. A missing sheet makes the parser fall back to the flat format silently.
- **An optional fifth `Provenance` sheet is inert to the parser.** `detect_format` uses a subset test; the parser resolves only the four named sheets, so provenance travels inside the uploaded file.
- **An artifact is served only from inside an artifact root.** `_safe_artifact_path` in `artifacts.py` resolves symlinks and requires `Path.relative_to` containment in `<BASE_DIR>/outputs` or `NEXTSEEK_OUTPUTS_DIR`. A string-prefix check, or a wider root such as `BASE_DIR` or home, lets a stored path read source or secrets.
- **`write_gate.py` and `read_safe_endpoints.json` stay side by side.** The loader resolves the JSON from the module's own directory, and `NessieAI/cc/op_registry/ops.py` reads it at import.

## Landmines

- **A missing or malformed allowlist fails every op as `AGENT_FAILED` with reason `internal` (502), never CONFIG_ERROR.** `build_gate(load_allowlist())` runs inside the op view's error handler (`_run_granular_op` in `nextseek_api/services/assistant.py`), and CONFIG_ERROR is not one of the op error codes (`nextseek_api/assistant/op_errors.py` `CODES`). The agent reads only "The op failed inside NExtSEEK."; the cause, `AllowlistMissingError`, is in the server log.
- **The write gate knows nine labels; the dispatch table has fourteen.** `SIDECAR_OPS` in `write_gate.py` holds the seven ported labels plus `graph-schema` and `aggregate`; `_HANDLERS` in `granular.py` holds every op. `run-ls`, `build-upload-xlsx`, `run-harvest` and `run-checksum` pass only because they never call the gate. The handlers that do call it are `api-read`, `api-write` and `upload-reingest`, and `upload-reingest` reaches the gate under the `api-write` label (see `nextseek_api/assistant/CONTRACT.md`).
- **`aggregate` answers with whatever finished 5 s inside its limit, and its parts keep running.** `run_op` passes the op's limit (`op_limits.py`: 90 s for graph, parse and aggregate, capped by the turn); `op_deadline_s` answers `ANSWER_MARGIN_S` before it. A part still running then is reported `timed_out` and finishes in the background on its pool thread. On the sidecar road the view caps every op at `SIDECAR_ROAD_CAP_S` (55 s), inside the sidecar's 60 s. Keep `aggregate.py` free of anything that builds or widens a scope: `NessieAI/tests/ns/test_aggregate_scope.py` checks its source. Under a turn pass the op keeps its slot until its last late part has finished, and each late part settles its own spend and failed models into the turn exactly once (plan 04); the answer never waits for them.
- **Patch the orchestrator at `NessieAI.ns.turn`, not at `nextseek_api.services.assistant`.** The NS pipeline bodies look `run_query`, `run_query_plan` and `run_pipeline_launch` up in `turn.py`. The services module deliberately does not import them, so a stale patch there fails loudly; re-adding the import would make it pass while the real orchestrator runs.
- **Keep `retry.py` free of a module-scope `chat_nextseek` import, and of `NessieAI.ns.turn`.** The evaluator tests stub `load_prompt` before `chat_nextseek.agents` is first imported, and the services module imports `retry.py` at load; `_get_orchestrator` keeps the orchestrator import inside the thread. No test runs `run_retry` itself (the retry tests mock `threading.Thread`), so a change to its body is checked by review only.
- **Nothing compares these wire models with the sidecar's copy** (`NessieAI/docker/ns-sidecar/app/granular_models.py`). Only a digest pin in `NessieAI/tests/cc/test_step7_sidecar_port.py` guards the sidecar file. A model change here drifts the sidecar silently.
