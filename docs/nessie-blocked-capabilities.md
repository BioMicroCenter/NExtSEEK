# Capabilities the nessie harness cannot assert

Generated 2026-08-04 from `nessie_tests/FAMILIES.json`. Companion to the 79 variants landed in `ce6e2dd`.

Of 366 capabilities across the 28 task families, **111 became variants**. This is the other **255**, and why each one is stuck.

| state | count | meaning |
|---|---:|---|
| `yes` | 111 | landed as a variant (32 more were near-duplicates and dropped) |
| `partial` | 49 | half the observable is reachable; a case would assert less than the capability |
| `no` | 84 | nothing in the criterion vocabulary reaches it |
| `needs_criterion` | 29 | prose names a real field but no criterion was written |
| `unit_lane` | 93 | reads as a pytest assertion over internal state, not an HTTP criterion |

## Why `unit_lane` is 93 of them

Those assertions came from the atlas gap run, whose agents were asked for "the single observable a test case would assert" **without** being given the closed corpus vocabulary. They wrote what a unit test would assert: `len(session['chat_log']) == 50`, `chat_log[0]['turn_id'] == 2`, `resolve_bundle_for_recall(session, ...)`. Those are good assertions in the wrong lane. They belong in `nessie_tests/tests/` or the subsystem's own suite, not in a corpus that drives an HTTP endpoint.

### The five already in the payload

These need no new plumbing, only for the harness to stop throwing them away:

- **`pipeline_agent.*`** — 17 of the 22 corpus criteria using it are already on `query_complete.debug` (`orchestrator.py:582` sets `debug_payload` from `pipeline/agent.py:52 snapshot_for_chat_log`: `active`, `pipeline_key`, `cohort_count`, `message_count`). The blanket prefix skip at `evaluate.py:372` discards them. Only the 5 `launch_plan.params.*` keys need more.
- **`cc_turn_meta.*`** — emitted as a progress event, already polled
- **`artifact_manifest.*`** — on `query_complete['files']`, dropped by `evaluate`
- **`route_model_class` / `route_reasoning`** — `route_observer` already reads them; `augment_debug` keeps three of five
- **`last_error`** — the `query_error` payload, already in the driver's hands

### The one that is genuinely missing

**`cc_ops_invoked`**: nothing records which `nextseek-*` binaries a container turn actually ran. That is why `pipeline_output_reingest`, `batch_upload_preparation` and `harmonization` can only ever be asserted on reply prose, and it is exactly the gap the 2026-08-04 CC probe hit when it could not confirm which ops harmonization calls. The trace exists inside the container and is written to `ChatSession.extra_state['cc_traces']`; it never reaches the `query_complete` payload.

### And one that is not a field at all

Six capabilities need the **corpus DSL** to carry `mode` and `force_route` per turn. `http_driver.drive` already accepts both; `e2e.catalog.Turn` is `(label, query, pass_criteria)` and `runner.py` never passes them. Without it, plan mode and any NS-only behaviour inside a CC-routed family are unreachable from the corpus.
